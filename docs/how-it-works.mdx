# How it works

## One run

1. When a session starts, the plugin adds its six tools and tells the model to use `run_code` for MCP calls.
   Hooks for the user interface draw the band and the rows of `add_hint`, `remove_hint` and `edit_hint`.
2. The model calls `run_code`. Claude Code does the normal permission check of this call.
3. The plugin checks the tool names and argument names in the program. If a name is wrong, the program does not
   run. See [The check before a run](./usage.mdx#the-check-before-a-run).
4. The plugin starts `runtime/runner.mjs` in a new Node process, the sandbox.
5. When the program calls a tool, the sandbox writes a request line to its standard output. `saveFile` and
   `readFile` also send a request line.
6. The plugin checks the nested call against your permission rules and then does it. See
   [Permissions](./permissions.mdx).
7. The plugin writes the result to a reply file in a temporary folder. The sandbox reads the file, and the program
   continues.
8. When the program returns, the plugin sends the [result](./usage.mdx#the-result) to the model and deletes the
   temporary folder.

The result goes back through a file, because the plugin API (`$.process.spawn`) writes the standard input of a
process only one time.

## Sandbox

The sandbox has four layers:

| Layer | What it stops |
| --- | --- |
| A Node `vm` context | The program has no `require`, `process`, `fetch`, timers or file system. Code generation from strings is off. The sandbox process does `sleep` with its own timer. The plugin writes and reads the files of `saveFile` and `readFile`, and reads the MCP resources. |
| The Node permission model (`--permission`) | The process can read only the runner file and its temporary folder. It cannot write files or start processes or workers. |
| `sandbox-exec` on macOS, `unshare -rn` on Linux | The process has no network access. |
| `ulimit -t` and a timer | A CPU limit stops busy loops. A wall-clock limit stops programs that wait too long. |

Only strings go between the host and the `vm` context. The global object of the context has no prototype. Thus the
program cannot get to the `Function` constructor of the host through `constructor.constructor`.

The `vm` module of Node is not a security boundary by itself. The other layers make the risk smaller.

On Linux, `unshare -rn` puts the process in a new user namespace and a new network namespace with no network. This
works only if the kernel lets a normal user make a user namespace. Ubuntu 24.04 and later do not, because of an
AppArmor setting. Then the process starts with no network block, but the `vm` context still has no `fetch`.

To see if the network block works on your machine, run this command. If it prints `ok`, the block works:

```bash
unshare -rn true && echo ok
```

The option `timeoutSeconds` sets the CPU limit and the wall-clock limit. The minimum is 5 seconds. See
[Configuration](./configuration.mdx).
